แนวคิดการเพิ่มประสิทธิภาพการดึงข้อมูลยอดขาย (Caching Strategy)

เนื่องจากตาราง ims_data_sale_sac_all มีข้อมูลจำนวนมหาศาล การคำนวณยอดขายย้อนหลัง (M-1, M-2, M-3) ทุกครั้งที่โหลดหน้าจอจะทำให้ระบบทำงานช้าลงมาก (Performance Bottleneck)

หลักการใหม่: "ใช้ฟิลด์ load_time เป็นตัวกำกับการโหลดข้อมูล เพื่อให้ระบบทราบว่าข้อมูลชุดนี้ถูกดึงมาจากยอดขายจริงแล้วกี่ครั้ง"

1. เงื่อนไขการจัดการข้อมูล (Data Flow Conditions)

สถานการณ์ การทำงานของระบบ
โหลดข้อมูลครั้งแรก (First Load) 1. ตรวจสอบฟิลด์ load_time หากเท่ากับ 0
2. ระบบจะดึงข้อมูลยอดขายจริงจาก ims_data_sale_sac_all เสมอ
3. บันทึกข้อมูลลงตารางหลัก และปรับค่า load_time = 1
การเปิดดูครั้งต่อไป (Subsequent View) ตรวจสอบพบ load_time > 0
ดึงข้อมูลจากตาราง ims_tires_plan_forecast โดยตรง ไม่ต้องคำนวณใหม่
การกดปุ่ม "ปรับปรุงข้อมูล" (Manual Sync) ดึงข้อมูลจริงมา Update ทับข้อมูลเดิม
ปรับเพิ่มค่า load_time = load_time + 1 เพื่อระบุว่าเป็นข้อมูลชุดที่อัปเดตล่าสุด

2. ขั้นตอนการทำงาน (Step-by-Step Implementation)

  • ปรับปรุงโครงสร้างการเก็บข้อมูล:

    เพิ่มคอลัมน์ load_time (INT, default 0) ในตาราง ims_tires_plan_forecast

  • ปรับปรุง API การดึงข้อมูล (Sync API):

    ในไฟล์ forecast_update_sales_data.php ให้เพิ่มการ Update load_time:

    SET p.sales_month_1 = s.total, ..., p.load_time = p.load_time + 1
  • แก้ไขหน้าจอแสดงผล (UI Update):

    เพิ่มปุ่ม ที่หน้าจอ forecast_plan_display_new.php:

    • เมื่อกดปุ่ม จะเรียกใช้ Refresh API ผ่าน Ajax
    • แสดง Loading Spinner ระหว่างประมวลผล
    • เมื่อเสร็จสิ้น สั่งให้ DataTable reload() เพื่อแสดงค่าใหม่ที่บันทึกแล้ว
  • ปรับจูนประสิทธิภาพการ Query:

    ในไฟล์ forecast_plan_fetch_new.php ให้ดึงข้อมูลจากฟิลด์ในตาราง p.* โดยตรง แทนการเขียน Sub-query ซ้อนข้างใน

3. ประโยชน์ที่ได้รับ

  • ความเร็ว: หน้าจอโหลดข้อมูลได้ทันที เพราะไม่ต้องคำนวณใหม่ทุกครั้ง
  • ความถูกต้อง: ข้อมูลไม่ล้าสมัยเพราะมีระบบ Sync ตามความต้องการของผู้ใช้
  • การลดภาระ Server: ลดการใช้ทรัพยากร CPU และ Memory ของ Database ในช่วงเวลาที่มีการใช้งานสูง
